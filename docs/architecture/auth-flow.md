# Authentication Flow

## Invitation Flow (organization invitations, Release 1.0 R1-3B)

An invitation is the way a **new** person joins **one named organization**. It is a hashed, expiring (7 days), revocable, single-use credential
issued by an authorized operator ([design record](../product/release-1.0-r1-3-organization-invitations.md)); accepting it atomically creates the
account (built-in `user` role only) **and** an ordinary, unapproved `member` membership. The organization-less invitation that preceded it
(`POST /invitations`, the users-page modal, plaintext tokens in `invitations`) is **retired**: its issuance route is gone and its links, password
registration and SSO branch all answer like an unknown token. The `invitations` table, its model and `users.invitation_id` were then **removed outright** (migration `2026_11_12_090000_retire_legacy_invitations`): Release 1.0 has no data to preserve and has not launched, so retired functionality is not carried for compatibility. A link from the retired flow is simply an unknown token.

```
Operator                          System                          Invitee
   │── Invite <email> to org ──────►│  (R1-3A: OrganizationInvitations::issue)
   │                                │── Store invitation (token HASH only) ─► DB
   │                                │── Queue encrypted mail, after commit ─► SMTP
   │                                │                               │
   │                                │               ◄── Click link ─┤
   │                                │   GET /invitation/{token}      │   (a READ: never consumes)
   │                                │── Hash, look up, check issuer ─┤
   │                                │── Page: org name, email (read-only) ─►│
   │                        Choose ─┤◄── Register with password ────┤
   │                        method  │       or  SSO (deferred for customers)
   │                                │── ONE transaction: issuer/org/invitation locks, account,
   │                                │   `user` role, password history, member, accepted ──►│ signed in
```

## Local Registration

1. The recipient opens the mailed link: `GET /invitation/{token}`. The token is hashed and resolved **only** in `organization_invitations`. Every dead
   link (unknown, malformed, expired, revoked, superseded, accepted, the address already has an account, the issuer is no longer authorized, a retired
   legacy token) renders the **same** `auth/invitation-invalid` page. Nothing is written.
2. The registration page shows the **organization's name**, the address (read-only) and the expiry. It exposes no id, no hash, no role.
3. The recipient submits `name`, `password`, `password_confirmation` (min 12 characters, complexity, not breached). **The address, the organization and the
   membership role are never read from the request**: they come from the locked invitation row. Extra fields are ignored.
4. The password is hashed **before** any lock is taken; `OrganizationInvitations::accept()` then runs the single atomic transaction. Any failure rolls
   everything back and leaves the invitation as it was; a refused attempt writes nothing and redirects to the same invalid page.
5. On success the user is signed in (the session is regenerated by the login) and redirected to the dashboard.
6. A failed validation redirects to `invitation.show` by name (not `back()`: the page sends `Referrer-Policy: no-referrer`, so the browser sends no
   `Referer`, and the token-bearing URL is deliberately not kept as the session's previous URL).

## OpenID SSO Flow

> **Release 1.0 (SSO completion) supersedes the deferral and "not implemented" statements below.** Customer SSO is enabled in `pilot` mode and still deferred in `closed`; Google and Microsoft are both functional where configured; the provider's verified-email evidence is required, failing closed, before an invitation is accepted; a confirmed second factor is asked for after a provider sign-in (no bypass); `identity_taken` has its own message. Design, flows, configuration and the live-verification list: [Release 1.0 SSO completion](../product/release-1.0-sso-completion.md). The older text below is kept as the history of the R1-3 decisions.

1. User starts Google/Microsoft authentication from login, Profile, or an invitation link.
2. The server stores a one-time OAuth intent (`login`, `link`, or `invitation`) and its target in the session.
3. Laravel Socialite redirects to the provider, which returns to `/auth/{provider}/callback`.
4. The callback consumes (`pull`) and validates the server-owned intent before performing exactly one operation:
   - Normal login authenticates only an existing `(provider, provider_id)` `SocialAccount`. Provider email is never used to find or automatically link a portal user.
   - Profile linking explicitly associates an unowned provider identity with the authenticated initiating user.
   - Invitation registration resolves the invitation **by the hash in the context**, then `OrganizationInvitations::acceptByHash()` revalidates the invitation, the issuer's authority and the provider's address against the invited one (one normalizer) under lock, and atomically creates the passwordless user, the `SocialAccount`, the `user` role and the ordinary membership.
5. Successful SSO login and invitation registration use Laravel's remember-me authentication unconditionally. Since Release 1.0 an account with a confirmed second factor is sent to the two-factor challenge instead of being signed in directly, and the session identifier is regenerated first.

**The invitation context** is `{intent: invitation, provider, initiatingUserId: null, invitationHash, startedAt}`:

- It holds the SHA-256 **hash** of the token, never the token. The hash is treated as a server-side credential too: it is never put in a redirect, an
  Inertia prop, a log line or a request parameter, and the callback never reads a token or hash from its own request.
- It is **one-time** (`pull`: gone after the callback whatever its outcome), **bound to its provider**, and good for
  `SocialiteController::INVITATION_CONTEXT_MAX_AGE_SECONDS` (10 minutes; a start time more than a minute in the future is refused too). A context in
  the retired shape (a plaintext `invitationToken`, no age limit) is refused for **every** intent.
- No failure rebuilds an invitation link from session state: a provider failure, a context that is old, foreign or malformed, an address mismatch and a
  dead invitation all end at the **login page** with "Open the link from your email again" or "This invitation is no longer available". (An address
  mismatch leaves the invitation open.) The one redirect that does name a link is the **deferred** answer at initiation, built from the token the request itself just carried.
- **SSO stays deferred for customers** in `closed` and `pilot` mode exactly as before: initiation answers with the password-only message and stores no
  context; a callback that somehow carries an invitation context is refused with no link.
- **Provider-email verification is a gate before customer SSO invitation acceptance is enabled (owner ruling, 2026-11-12). It is NOT implemented today.** The callback compares the provider's address with the invited one (one normalizer) but does not check that the provider *verified* it. What the providers give, from this repository's dependencies:
  - **Google** (`laravel/socialite` `GoogleProvider`): the user data carries the OpenID `email_verified` claim (exposed as `$socialUser->user['email_verified']`, and `verified_email` for compatibility). It can be required and refused when it is not exactly `true`. Supported.
  - **Microsoft: unsupported today, in two ways.** (1) **No Microsoft driver exists**: `laravel/socialite` ships none, `socialiteproviders/microsoft` is not installed and no `Socialite::extend` registers one, so `Socialite::driver('microsoft')` throws `Driver [microsoft] not supported` (a 500 on initiation, a provider-failure redirect in the callback); the provider is only listed in `SUPPORTED_PROVIDERS` and the UI. (2) **If a driver is added**, Microsoft's `mail` / `userPrincipalName` values carry no `email_verified` claim and can be unverified or attacker-controlled for accounts from a tenant the attacker administers (the "nOAuth" class). Verification would need a tenant-restricted app registration and the `xms_edov` optional claim, or Microsoft acceptance stays refused. This was reasoned from the provider's published behaviour, not exercised: no Microsoft driver is available to test against.
  - The requirement is not weakened: until a provider-specific, fail-closed check exists, SSO invitation acceptance must stay disabled for customers (it is, in `closed` and `pilot` mode), and a provider that cannot assert verification is recorded as unsupported rather than trusted.

## Security contract clarifications (stated for the independent review; nothing here is a claim the tests do not support)

**1. The hash-only SSO context.**
- *Is the hash persisted in the session store?* **Yes.** `oauth_context` is a session attribute; with the `database` driver it is serialized into `sessions.payload` (encrypted at rest only if `SESSION_ENCRYPT=true`, which the shipped `.env.example` sets and `config/session.php` does not default to). It stays there from initiation until the callback `pull`s it, the next `sso.redirect` `forget`s it, or the session row expires or is collected (`SESSION_LIFETIME`, 480 minutes in `.env.example`). The 10-minute maximum age is enforced when the context is **read**, so an old hash can sit in a payload but is inert.
- *Can it be a bearer credential?* **Not on the web surface.** No route reads a hash from a request: the callback ignores its query (tested), the page and POST take the plaintext token and hash it, so submitting a hash as a token hashes it again and matches nothing. The hash cannot be turned back into a link (SHA-256 of ~380 bits of CSPRNG output). It is the **same value** already stored in `organization_invitations.token_hash`, so the session copy discloses nothing the table does not.
- *What it does act as:* a **session-bound capability**. Whoever controls that session (its cookie, which is encrypted with `APP_KEY`) and then completes a provider sign-in whose address equals the invited address can accept the invitation without presenting the link again; that is the same person who started the flow with the link. Someone with database **write** access to `sessions` could plant a context in a session they control, but they could equally insert an invitation row directly, and they would still need a provider identity for the invited address.
- *What is not enforced at runtime:* `OrganizationInvitations::acceptByHash()` is public and is called only by the callback today (a source search shows no other caller); no fence pins "only the callback", it is a convention.

**2. `ProtectInvitationCredential` and the prefetch-based session-history protection.**
- *What it does exactly:* before the route runs it sets `Sec-Purpose: prefetch` on the **inbound request object**; after the route it sets `Referrer-Policy: no-referrer` and `Cache-Control: no-store` on the response. `StartSession::storeCurrentUrl()` (which runs after the whole route stack returns) skips a request for which `Request::prefetch()` is true, so the token-bearing URL is not written as `_previous.url`.
- *What this relies on:* framework internals (`storeCurrentUrl` honouring `prefetch()`, and the middleware running before any short-circuit). A test reads the real `sessions` table and has a control proving an ordinary page *is* recorded; ordering is covered for a signed-in user redirected by `guest`, a customer refused by the pilot gate (404), a 429 and a database failure (500). A framework change that stops honouring the mark fails the test; it does not fail safe by itself.
- *Side effects:* the inbound request claims to be a prefetch for the rest of that request, and **two** framework components read that mark, not one:
  1. `StartSession::storeCurrentUrl()` (the intended use, above).
  2. **Inertia's server middleware** (`Inertia\Middleware::handle`). For an Inertia request whose redirect `Location` contains a URL fragment (`#`) it normally answers `409` with `X-Inertia-Redirect`, so the client performs a full-page visit that preserves the fragment; for a request that is a prefetch it **skips** that conversion and lets the plain redirect through.

  Why (2) does not affect these routes today: none of the redirects they issue carries a fragment. The registration POST redirects to `invitation.show` (validation failure, dead link) or `dashboard` (success); `guest` redirects a signed-in user to the dashboard; the SSO initiation redirects to the provider's authorization URL (an OAuth authorization URL carries its parameters in the query string, not a fragment) or to `login`. A test sends each of these as an Inertia request and asserts a redirect with no `#` and no `409`. If a route in this group is ever changed to redirect with a fragment, an Inertia client would receive the plain redirect instead of the 409 and the fragment handling would silently differ; that test is the tripwire, and the middleware is not redesigned for a hypothetical. Apart from these two readers, nothing in this application reads `prefetch()` or `Sec-Purpose` (a search of `app/` and `resources/js` confirms; the frontend's own `prefetch` link attribute is unrelated and is not used on these pages), but a future reader would be misled on these three routes.
- *What it does NOT protect:* the token in the page it renders (the Inertia `token` prop and `url`, needed for the form action and the provider links); the URL in shared-host access logs, browser history and the mailbox; a response produced before the middleware runs (an earlier middleware in the web group, or the global stack, that answers first). It covers only the three token-bearing routes: the SSO callback carries the provider's `code` and `state`, not our token.

**3. `WithholdsQueryDetails`.**
- *What it catches:* only `Illuminate\Database\QueryException`, thrown by the closure it wraps (the invitation lookup, or the whole `accept` / `acceptByHash` call). Laravel wraps a driver error raised while running a statement as a `QueryException`, whose message embeds the SQL **with its bindings** (the hash). (A failure to connect at connection time may surface as a different exception type; that was not tested.)
- *What it does:* `report()`s a **new** `App\Exceptions\InvitationDatabaseFailure` (a `RuntimeException` with a constant message, no SQL, no bindings, **no chained previous exception**) and `abort(500)`. The 500 `HttpException` is not reported again, so there is one log entry. The original exception is not retained by it.
- *What stays diagnosable (R1-3B remediation F1).* The report carries, as structured log context (`invitation_database_failure`), an **allowlist** of fields, each a bounded, validated scalar: the SQLSTATE (`errorInfo[0]`), the driver error code (`errorInfo[1]`), the violated key's **name** for a duplicate entry (`DuplicateKey::name()`, a schema identifier; `null` when it cannot be read, never a guess), the connection name, the original exception's class, and the original stack as `file:line Class->function` strings (the thrown location first, paths relative to the application root). An operator therefore sees *why* the operation failed, including the unknown-duplicate-key case R1-3A wanted visible, without the credential.
- *What is never reported:* the original exception's message, `errorInfo[2]` (the driver's text, which for a duplicate entry quotes the duplicated **value**: a hash or an e-mail address), the SQL, the bindings, any trace **argument** (a frame argument can be the plaintext token: the controller method takes it), or the original exception as `previous`. The report's *own* stack trace is captured beneath the controller frame, so it is constructed with `zend.exception_ignore_args` switched on for that instant and restored at once; it therefore carries no arguments **where the runtime override is permitted** (PHP's default, and a development image's, is to capture them). **Limitation:** the override is an `ini_set()`; a host configuration that forbids runtime overrides can prevent it, and the report's own trace would then carry the arguments again. This covers the wrapped database failures only; every other exception depends on the production PHP configuration, so verifying `zend.exception_ignore_args` on the real host is a **mandatory Release 1.0 readiness gate** (design record 19.9, obligation 6). The *original* exception, which the framework never logs here, still holds them in memory until it is discarded.
- *Limits, stated plainly:* the diagnostic is bounded to the fields above, so a driver condition that is only explained by the SQL or the driver's text (for example, which column's value was too long) is not recoverable from the log. The HTTP answer stays a generic 500 and no field is shown to the client. Production `php.ini` handling of exception arguments for *other* exceptions and the web server's access log are separate obligations (design record 19.9).
- *Rollback:* it runs outside any transaction. `accept` / `acceptByHash` open their own `DB::transaction` (retried up to three times on a deadlock); by the time a `QueryException` leaves it the transaction has already rolled back, so the trait changes no database state and turns no failure into a success. It does not catch other `Throwable`s (for example R1-3A's `LogicException`), which are reported normally and carry no binding.
- *What it does NOT cover:* a `QueryException` raised before the controller runs (the session store, the throttle's cache store) carries other bindings (a session id, a hashed limiter key), not the token or hash; and it does not stop the SQL being recorded by a database query log or slow-query log on the server.

## Invitation credential protections (R1-3B)

Three requests carry the token in their URL: `GET`/`POST /invitation/{token}` and `GET /auth/{provider}/redirect?invitation=` (the last **only** when it
carries an `invitation` query; ordinary SSO login is untouched).

- **Response headers** (`ProtectInvitationCredential`, outermost on these routes, so also on a 429 and on the redirect to the identity provider):
  `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.
- **Document-level referrer policy** (R1-3C review remediation). The header alone is not enough: a proxy may append its own `Referrer-Policy`, and a browser applies the **last** value
  (the development nginx did, and Chromium then sent the full invitation URL as the `Referer` of same-origin requests, which nginx logged). The middleware therefore also sets the request attribute
  `credential_response`, and the Inertia root (`app.blade.php`) renders `<meta name="referrer" content="no-referrer">` immediately after `<meta charset>` when it is set, so the document's own policy
  holds whatever a proxy adds. Ordinary pages never carry the tag. The development nginx supplies its default only when the application sent none. The production web server's behaviour and access-log
  handling remain a preproduction requirement.
- **Not in the session.** The framework stores every full-page GET's URL in the session store as the "previous URL". The middleware marks these requests
  as prefetches before they run (the framework's own switch for "not a navigation to remember"), so the token-bearing URL is never recorded, not even
  when a signed-in user opens the link and `guest` redirects them away. A test reads the real `sessions` table, including after a request the throttle answers with 429 and after one that ends in a database failure (500), each with only that request's own persisted row present.
- **Throttles**, keyed by client IP only (never by token or address): `invitation` 60/min (the page), `invitation-register` 20/min (the POST: it also calls
  the compromised-password service and hashes a password), `invitation-sso` 30/min (only with an `invitation` query; `Limit::none()` otherwise).
- **Client-IP assumption (documented, not changed).** No trusted proxy is configured, so `$request->ip()` is the immediate peer, as for the `login` and
  `two-factor` limiters. If the shared host's web server forwards every request from one address, a per-IP limiter degrades into a **global** one and
  gives no per-client protection; the limits are generous for that reason. Staging step: observe the peer address the limiter keys on before trusting the limits.
- **Logs.** A `QueryException` embeds its bindings, and an invitation lookup binds the hash. On every path that looks an invitation up, a database
  failure is reported as "An invitation database operation failed; query details were suppressed." with an allowlisted diagnostic (SQLSTATE, driver code, violated key name, connection, original class, call-site locations without arguments) and answered with a plain 500 (`WithholdsQueryDetails`, `InvitationDatabaseFailure`).
  The plaintext token and the hash are otherwise never written to the application log, the activity log, a table other than `organization_invitations.token_hash`, or the session.
- **Residuals, unchanged and accepted:** the token is in the URL, so shared-host access logs hold it (bounded by 7 days, single use, revocation); it is in the mailbox, the encrypted queue payload and `failed_jobs`, and in the SSO initiating request's query.

## Session Security

- Browser sessions are stored in the database; Redis remains available for cache and queues.
- Signing out other browser sessions deletes their database rows and rotates the user's remember token, while preserving the current session.
- Session cookie: `HttpOnly`, `Secure`, `SameSite=Lax`
- Absolute session timeout: 8 hours (configurable)
- Idle session timeout: 2 hours (configurable)
- Session ID regenerated on privilege escalation (login, 2FA success)

## Password Reset Flow

1. User requests reset at `/forgot-password`
2. System sends a signed, time-limited URL (60 min) to the email
3. User clicks `/reset-password/{token}` link → reset form shown
4. New password validated (same rules; checked against last 5 hashes)
5. Password updated; all sessions invalidated
6. User is redirected to login and signs in with the new password

## 2FA Flow (TOTP)

1. User enables 2FA from profile settings
2. QR code displayed for authenticator app setup
3. User confirms with a valid TOTP code
4. Recovery codes generated (8 × 16-char codes) — user must download
5. On login after 2FA is enabled:
   - Credentials verified → 2FA challenge screen shown
   - TOTP or recovery code required
   - On success → session established

## Account Suspension (Release 0.9, H3)

A suspended account (`users.disabled_at` set) cannot sign in by password, two-factor challenge, remembered login,
existing session, SSO, password reset or invitation acceptance; to an unauthenticated caller it looks exactly like an
account that does not exist. Suspension and reactivation sign the user out everywhere. The entry-point inventory, the
enforcement mechanism for each, and the last-active-administrator rule are in
[Account Lifecycle](./account-lifecycle.md).
